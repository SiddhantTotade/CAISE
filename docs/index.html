Talk to your code.

CAISE indexes your Git repositories into a vector database. Ask a question in plain language, CAISE retrieves the most relevant code, and an LLM of your choice — local or cloud — answers using only that code, with access control built in.

Introduction

Understanding a large codebase means searching by meaning, not only by keyword. CAISE combines semantic search with a large language model so developers can onboard, navigate and audit code through conversation.

🔎

Semantic search

Code is chunked and embedded with sentence-transformers, then stored in Qdrant for cosine-similarity retrieval.

💬

Grounded answers

The LLM answers using only the retrieved snippets and cites file paths and line numbers.

🔐

Private by design

Run fully local with Ollama and Qdrant, or bring your own cloud keys. Users only retrieve repos they can access.

Features

Everything needed to go from a repository URL to a conversation about its code.

🌿

Per-branch indexing

One checkout and one index per repo@branch, so branches are searchable independently.

⚡

Incremental re-index

Diffs the last indexed commit against HEAD and re-embeds only modified and added files, dropping deleted ones.

🌳

AST-aware chunking

Python is split into function and class chunks with tree-sitter; other languages use 100-line blocks.

🤖

Multi-provider LLMs

Ollama, OpenAI, Anthropic and DeepSeek with a model catalog per provider and live configured flags.

📡

Streaming chat

Server-Sent Events stream tokens and sources; chats, partial answers and failures are persisted server-side.

🛡️

Security scanning

Every index run executes a Semgrep scan and reports rule, severity, file and line for each finding.

🔑

Bring your own keys

Signed-in users can save OpenAI/Anthropic/DeepSeek keys, stored Fernet-encrypted and never returned in full.

🪝

GitHub webhook

A signed push webhook re-indexes registered branches automatically.

👤

OAuth & guest mode

Sign in with GitHub, or continue as a guest limited to public repositories on allow-listed hosts.

Use cases

Where CAISE saves time.

🚀 Developer onboarding

“Where is authentication handled?” “How does the indexing pipeline work?” New teammates get cited answers instead of reading every file.

🧭 Navigating large repos

Find code by intent — “where do we retry failed requests?” — even when you don't know the identifier names.

🔍 Change awareness & review

Each index run records which files were modified, added and deleted since the previous commit, shown in the workspace context drawer.

🛡️ Security triage

Semgrep findings with severity and location are produced for every indexed commit, giving a fast starting point for audits.

🏠 Private, on-prem AI

Pair Ollama with a self-hosted Qdrant so source code never leaves your machine or network.

📚 Team knowledge base

Index many repositories and branches, then ask across all of them or scope a chat to a single repo@branch.

How it works

From repository URL to streamed answer in five steps.

  1. IngestThe repo is cloned (or pulled) into storage/repos/<org>/<repo>@<branch>. Private repos use a token that is used per run and never stored.
  2. ChunkPython files are split by AST into functions/classes. .js .ts .java .go .rs .md .json use 100-line blocks. Symlinks are never followed.
  3. Embed & storeChunks are embedded with all-MiniLM-L6-v2 (384-dim, cosine) and upserted into Qdrant along with the list of users allowed to read them.
  4. Update incrementallyLater runs diff the last indexed commit against HEAD. Unchanged → skipped. Previous commit gone (force-push) → full re-index.
  5. AskThe question is embedded, top-k chunks the caller may access are retrieved, and the selected LLM streams an answer with sources over SSE.

Architecture

A React single-page app talks to a FastAPI backend; slow indexing runs out-of-band on Celery workers.

FastAPI

REST + SSE API, GitHub OAuth, chat persistence, key management and the webhook receiver.

Celery + Redis

Indexing is queued and polled via /task-status/{id}, so the UI stays responsive on big repos.

Qdrant

Embedded (local) for single-process dev, or a server (server) — required when API and worker run together.

Installation

Requires Python 3.12+, Node.js 20+, Git, Redis and Qdrant. Ollama and a GitHub OAuth app are optional (guest mode works without OAuth).

1 · Backend

git clone <repo-url> CAISE && cd CAISE
python3 -m venv venv && source venv/bin/activate
pip install -r caise-backend/requirements.txt   # large: includes torch

2 · Redis & Qdrant

docker run -d --name caise-redis -p 6379:6379 redis:7
docker run -d --name caise-qdrant -p 6333:6333 -p 6334:6334 \
  -v "$(pwd)/qdrant_storage:/qdrant/storage" qdrant/qdrant

3 · Configure caise-backend/.env

ENVIRONMENT=development
SECRET_KEY=<python -c "import secrets; print(secrets.token_urlsafe(48))">
FRONTEND_URL=http://localhost:3000
GITHUB_CLIENT_ID=<oauth client id>
GITHUB_CLIENT_SECRET=<oauth client secret>
GITHUB_REDIRECT_URI=http://localhost:8000/api/v1/auth/github/callback
CELERY_BROKER_URL=redis://localhost:6379/0
CELERY_RESULT_BACKEND=redis://localhost:6379/0
QDRANT_MODE=server
QDRANT_HOST=localhost
DEFAULT_LLM_PROVIDER=ollama
DEFAULT_LOCAL_MODEL=qwen2.5-coder:32b

4 · Local model optional

ollama pull qwen2.5-coder:32b

5 · Frontend

cd caise-frontend
cp .env.example .env     # VITE_BACKEND_URL, VITE_DEV_PORT=3000, VITE_API_PREFIX=/api/v1
npm install

6 · Run (three terminals)

# API
cd caise-backend && uvicorn app.main:app --reload --port 8000
# Indexing worker
cd caise-backend && celery -A app.core.celery.celery_app worker --loglevel=info
# Frontend
cd caise-frontend && npm run dev

Open http://localhost:3000 · API docs at localhost:8000/docs.

Tip: run backend commands from caise-backend/. The first search/index downloads the embedding model once. Use QDRANT_MODE=server when the API and worker run together — the embedded store allows one process only.

Security model

Designed so that code, credentials and keys stay where they belong.

Access control

Every vector stores allowed_users; searches filter on the caller. Access is granted only after a clone/pull succeeds with the user's own credentials.

Sessions & CORS

JWT in an HttpOnly, SameSite=Lax cookie (Secure in production). CORS permits only FRONTEND_URL.

Secrets

Repo tokens are per-run and stripped from .git/config. Saved LLM keys are Fernet-encrypted; only a 4-char hint is shown.

Input hardening

Repo URLs and git refs are allow-list validated; git runs without a shell; symlinks are not followed.

Webhook

HMAC-SHA256, constant-time comparison; disabled until a secret is configured.

Provider errors

Upstream error text is never forwarded to clients, since it can echo credentials.

Production checklist

  • Set ENVIRONMENT=production, a strong SECRET_KEY, and a dedicated API_KEY_ENCRYPTION_KEY (rotating either invalidates saved user keys).
  • Serve the built frontend and /api from one origin behind a TLS reverse proxy; disable buffering for SSE.
  • Use QDRANT_MODE=server and a Redis reachable by both API and worker.
  • Update FRONTEND_URL, GITHUB_REDIRECT_URI and the OAuth app callback to public URLs.
  • Back up caise_metadata.db and the Qdrant volume.

FAQ & troubleshooting

Common questions and fixes.

“Storage folder is already accessed by another instance of Qdrant client”

Embedded Qdrant allows one process. Set QDRANT_MODE=server and run Qdrant in Docker.

Indexing never leaves “queued”

Redis isn't running or no Celery worker is started. Start both and retry.

Login redirects loop / CORS errors

FRONTEND_URL in the backend must equal the frontend origin (http://localhost:<VITE_DEV_PORT>).

provider_not_configured (503)

There is neither a server-side key nor a saved user key for that cloud provider. Add one in .env or Settings.

Ollama requests fail with provider_unreachable

Ensure Ollama is running, OLLAMA_BASE_URL is correct and the model has been pulled.

“Model … is not available for provider …”

Add the model to the matching AVAILABLE_*_MODELS variable.

Does my code leave my machine?

Not with Ollama and a local/self-hosted Qdrant. With cloud providers, retrieved snippets are sent to that provider as prompt context.

Limitations

AST-aware chunking is Python-only; supported file types are .py .js .ts .java .go .rs .md .json; only http(s) Git remotes; Semgrep findings are returned in the index task result and are not persisted.
